# Cobblemon Dynamics Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for
> tracking. Read this index first, then the milestone file of the task you execute.

**Goal:** Build and test the v1 scope of Cobblemon Dynamics 1.0 (milestones M0 to M5) until every Phase 1
`MUST` and `MUST NOT` row of the spec sheet has a passing test, then stop at the Phase 1 gate for the
approver's play-test.

**Architecture:** One NeoForge 1.21.1 mod in Kotlin, with Java mixins. A server-side work engine owns every
worker's state, a global claim registry gives one worker one target, data-driven role files map Pokémon
types to target handlers, and a Brain activity moves and holds the workers. The engine's rules are pure
Kotlin classes with unit tests on a fake clock. GameTests run the same code against real Cobblemon, Create
and AE2 blocks and entities.

**Tech Stack:** Minecraft 1.21.1, NeoForge 21.1.265 (runtime floor 21.1.219), ModDevGradle 2.0.148,
Gradle 9.2.1, Kotlin 2.2.20, KotlinForForge 5.10.0, Cobblemon 1.8.4, Create 6.0.10 (build 280), AE2
19.2.19, JUnit 5, NeoForge GameTests, GitHub Actions.

**Spec:** [`docs/plans/2026-11-09-v1-spec-sheet.md`](2026-11-09-v1-spec-sheet.md). Design context:
[`ARCHITECTURE.md`](../../ARCHITECTURE.md), [`docs/adr/`](../adr/), and the integration facts in
[`docs/research/2026-11-09-integration-points.md`](../research/2026-11-09-integration-points.md). If this
plan and the spec sheet disagree, the spec sheet wins. Fix the plan in the same pull request.

- One package (`pasture`) holds every read of Cobblemon pasture internals (ARCHITECTURE section 1).
- Cobblemon models and textures are never copied. All art is original 16 × 16. Phase 1 may ship
  placeholder art (CD-ART-11).
- Engine work runs on the server thread only.

## How to execute this plan

1. Work milestone by milestone, in order: M0, M1, M2, M3, M4, M5. Each milestone is one branch and one pull
   request into `main`: `m0-scaffold-ci`, `m1-engine-leash-stoker`, `m2-stamina-beds-healers`,
   `m3-create-roles`, `m4-vanilla-fe-roles`, `m5-ui-compat-gate`.
2. Inside a milestone, execute the tasks in their numbered order. Each task is test-first: write the
   failing test, run it and see it fail for the expected reason, write the code, run it and see it pass,
   then commit.
3. At the start of each milestone, check every API reference that its tasks use against the jars that
   Gradle downloaded (`build/moddev/artifacts/` and the Gradle cache). Where the code differs from the
   plan, fix the plan text in the same commit as the code. The research note marks inferred facts with
   "(inferred)". Treat those as unverified.
4. A task is done when its tests pass, `./gradlew build` passes, and the GameTests that it adds pass in
   `./gradlew runGameTestServer`. A milestone is done when its pull request is green in CI, every review
   thread is resolved, and it is merged.
5. Cite the spec rows in code only where a comment states a non-obvious invariant. Rows are cited in test
   names (`CD-ASG-06 passes start at the first boundary after completion`) and in commit messages.
6. Test scope. Approver ruling, 2026-11-09: "avoid game tests for high-confidence code. I'd rather test at
   the end and fix." Unit tests stay test-first. Write a GameTest only where the behaviour against real
   Cobblemon, NeoForge, Minecraft or Create is uncertain: the Brain and AI, Create kinetics and mixins, and
   undocumented platform behaviour. For other code, such as registrations, data files, payloads,
   commands, config plumbing and simple block entity reads and writes, defer the planned GameTest:
   - Mark the row in the task text: "GameTest deferred (high confidence): verified in the end-of-phase pass".
   - Add the row to the deferred list in M5 Task 9.

   Run the full GameTest suite once at the end of each part of a milestone, not after every task.

Commands (Windows: `gradlew.bat`; Unix: `./gradlew`):

| Purpose | Command | Pass condition |
| --- | --- | --- |
| Compile, unit tests, jar checks | `./gradlew build` | `BUILD SUCCESSFUL` |
| One unit test class | `./gradlew test --tests "codes.honor.cobblemondynamics.claim.ClaimRegistryTest"` | `BUILD SUCCESSFUL` |
| GameTests (full mod set) | `./gradlew runGameTestServer` | exit code 0, log line `All N required tests passed` |

## Test architecture

**Unit tests** (`src/test/kotlin`). JUnit 5 with no game bootstrap. They may use plain value classes from
Minecraft (`BlockPos`, `Vec3`, `ResourceLocation`, `AABB`), but never registries, `Level` or Cobblemon
classes. Every engine rule that the spec tests "on a fake clock" lives in a pure class that takes the
current tick as a parameter.

**GameTests** (`src/gametest`). A separate test mod, `cobblemon_dynamics_test`, joins only the
`gameTestServer` run. The release jar never contains it (`verifyJar` checks this). Test classes carry
`@GameTestHolder("cobblemon_dynamics")` and `@PrefixGameTestTemplate(false)`, have a public no-argument
constructor and use instance methods. Templates are empty stone-floor structures under
`src/gametest/resources-shared/data/cobblemon_dynamics/structure/` (shared with the core run from M3),
generated by `scripts/gen_test_structures.py`:

| Template | Size (x × y × z) | Use |
| --- | --- | --- |
| `floor_9x5x9` | 9 × 5 × 9 | single-block handler tests |
| `floor_15x6x15` | 15 × 6 × 15 | one pasture, nearby targets |
| `floor_23x10x23` | 23 × 10 × 23 | work-area edges at offsets 8 and 9 |
| `floor_23x17x23` | 23 × 17 × 23 | vertical offsets 6 and 7 |
| `floor_41x8x41` | 41 × 8 × 41 | two pastures, Telekinesis-style ranges |

`TestKit` (M0 Task 3, grown in later tasks) builds every scene: a mock owner player, a pasture placed
through `PastureBlock.setPlacedBy`, a Pokémon created with `PokemonProperties.parse(...)`, added to the
owner's PC and tethered with `PokemonPastureBlockEntity.tether(...)`. The test mod sets the game rules
`doPokemonSpawning=false`, `doDaylightCycle=false` and `doWeatherCycle=false`, and the time to 6000 at
server start, so wild spawns and night sleep never touch a test.

GameTests cannot restart the server or unload a test chunk. Rows that say "restart" or "unload" use these
equivalents in GameTests, and the isolated test pack repeats them for real:

- Restart: save the block entity or the Pokémon to NBT, load it into a fresh object, and call
  `WorkEngine.resetRuntimeForTest()`, which drops every in-memory claim, worker and pending selection.
- Chunk unload: call `EngineEvents.onChunkUnload(level, chunkPos)`, the same function that the
  `ChunkEvent.Unload` subscriber calls.

**Run matrix.** `gameTestServer` loads Cobblemon, KotlinForForge, Create (with Ponder, Flywheel and
Registrate) and AE2 (with GuideME). M3 adds `gameTestServerCore` with Cobblemon and KotlinForForge only.
M5 adds `gameTestServerCobbleworkers` and `gameTestServerCobblebase` for the compat rows. CI runs every
run.

**Isolated test pack** (`scripts/testpack/`, M0 Task 6). A clean NeoForge 21.1 dedicated server folder
under `run/testpack/` (ignored by git), with only the mods that a scenario needs, downloaded from Modrinth
at pinned versions with SHA-512 checks. It never uses the approver's COHO modpack. The script installs
NeoForge, copies the freshly built jar, starts the server with RCON on `127.0.0.1`, runs a scenario of
commands, reads the log and stops the server. Scenarios cover the dependency-range demos (CD-PLAT-01,
CD-PLAT-02, CD-PLAT-03, CD-PLAT-05), real restarts and the PERF measurement. The approver's play-test uses
a client instance that the script assembles from the same pinned jars.

## Rows that this plan handles in a special way

- **Telekinesis inside Phase 1 rows.** CD-LSH-16 to CD-LSH-20 and CD-SEC-11 are Phase 1 rows whose tests
  name the Telekinesis role, which ships in Phase 2 (M6). The leash code in M1 handles any role whose
  handler declares `BindingShape.SOURCE_AND_DESTINATION`. The GameTests use a test-only role
  `cobblemon_dynamics:test_transfer` (types `psychic`, handler `cobblemon_dynamics:test_transfer`, item
  handler targets) that the test mod registers. CD-LSH-16 is a unit test with constructed role
  definitions named `pump` and `telekinesis`. M6 re-runs these tests with the real role file.
- **CD-BAL-05** checks the Telekinesis and Magnet role files, which do not exist in Phase 1. Its check
  script passes when the files are absent and becomes binding in M6.
- **CD-REL-14 and CD-REL-15** are Phase 2 and Phase 3 gates. This plan records them as out of scope.
- **Demo rows** that need a human view of the client (animations, the panel, head bars, action-bar text)
  go to `docs/testing/manual-checklist.md` (M5 Task 8) and the approver's play-test. Each such row also has
  the strongest automated check available, for example a GameTest that asserts the action-bar component
  that the server sent.
- **Analysis rows** (CD-BAL-01, CD-BAL-02, CD-BAL-03, CD-BAL-07, CD-PERF-01, CD-PERF-02, CD-PERF-05) get a
  unit test or a scripted measurement that computes the stated value.

## Coverage check

`scripts/check_plan_coverage.py` (M0 Task 1) reads the spec sheet, selects every row outside the TLK, MAG,
FAN, TLW and ART areas, and checks that some task in the six milestone files cites it. Run it after any
plan edit. It prints each missing row and exits non-zero when one is missing.
