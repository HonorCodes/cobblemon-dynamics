# Cobblemon Dynamics Phase 2 Implementation Plan

> Read this index first, then the milestone file of the task you execute. Steps use checkbox (`- [ ]`) syntax for
> tracking.

**Goal:** Build and test the v2 scope of Cobblemon Dynamics 1.0 (milestones M6 to M8, and Quick Work before the end of
M8). That is the Telekinesis, Magnet, Fan Catalyst and Tailwind roles, Quick Work for party Cobblemon, the final art, and
the Phase 2 parts of Phase 1 rows. Work until every `MUST` and `MUST NOT` row of the spec sheet has a passing test on one
commit. Then stop at the Phase 2 gate for the approver's play-test and art review.

**Architecture:** The four roles plug into the Phase 1 engine as leash-only target handlers. Telekinesis and the Magnet
move items in 20-tick batches through one pure batch planner over NeoForge item handlers. The Fan Catalyst registers its
own Create fan processing types and exempts its worker from the air current through a mixin. Tailwind adds virtual sails
to a windmill through a mixin on its speed. Both Create states sync to clients through Create block entity behaviours.
The art comes from text sources under `art/`, which a standard-library script renders, checks and shows on one review
spritesheet. Quick Work runs one order for each party Cobblemon that its owner sends out at a block, in a small runtime of the
work engine with one worker, a work area around the block and no scan.

**Tech Stack:** Minecraft 1.21.1, NeoForge 21.1.265 (runtime floor 21.1.219), ModDevGradle 2.0.148, Gradle 9.9.0,
Kotlin 2.2.21, KotlinForForge 5.10.0, Cobblemon 1.8.4, Create 6.0.10 (build 280), AE2 19.2.19, MixinExtras 0.5.5 (from
NeoForge), JUnit 6.1.3, NeoForge GameTests, Python 3.12 (standard library only), GitHub Actions.

**Spec:** [`docs/plans/2026-11-09-v1-spec-sheet.md`](2026-11-09-v1-spec-sheet.md), with the amendments in
[Spec amendments that this plan carries](#spec-amendments-that-this-plan-carries). Design context:
[`ARCHITECTURE.md`](../../ARCHITECTURE.md) (sections 4, 6, 8 and 11 hold the Phase 2 design), [`docs/adr/`](../adr/)
(ADR-0006, ADR-0007, ADR-0011, ADR-0012, ADR-0013), [`docs/roles.md`](../roles.md) and
[`docs/research/2026-11-09-integration-points.md`](../research/2026-11-09-integration-points.md). The model is the
[Phase 1 plan](2026-11-09-phase-1-plan.md). If this plan and the spec sheet disagree, the spec sheet wins. Fix the plan
in the same pull request.

## Global Constraints

Every task's requirements include these lines. Values are copied from the spec sheet.

- NeoForge is a required dependency with range `[21.1.219,)` (CD-PLAT-01).
- Cobblemon is a required dependency with range `[1.8.4,1.9)` (CD-PLAT-02).
- `modLoader = "kotlinforforge"` and `loaderVersion = "[5.10,)"` (CD-PLAT-03).
- Every class in the jar is Java 21 bytecode, major version 65 (CD-PLAT-04).
- Create `[6.0.10,6.1)` and AE2 `[19.2,20)` are optional dependencies (CD-PLAT-05).
- The mod is required on both the client and the server (CD-PLAT-06).
- Mod id `cobblemon_dynamics`, Maven coordinates `codes.honor:cobblemon-dynamics`, root package
  `codes.honor.cobblemondynamics` (CD-PLAT-07, R48).
- Cobbleworkers and Cobblebase are never required dependencies (CD-PLAT-08).
- Release versions read `MAJOR.MINOR.PATCH+mc1.21.1`. Phase 2 builds use tags `vX.Y.Z-beta.N`, and only a tag with no
  suffix publishes (CD-REL-05, CD-REL-12, R56).
- Code license MPL-2.0. `neoforge.mods.toml` declares `license = "MPL-2.0"` (CD-REL-06). Every asset carries the MPL-2.0
  license (CD-ART-13).
- The jar holds no file under `assets/cobblemon/` (CD-REL-07).
- The main source set never imports from `appeng` and has no AE2 compile dependency (CD-CRY-05).
- Every player-facing string comes from a lang key, and `en_us` is complete. UI code has no `Component.literal` call
  (CD-UI-12). The stat label is always "Work Stamina" (CD-UI-11).
- No INFO-level or higher logging from per-tick code. A failing hook logs one warning per cause (CD-PERF-05).
- Claims are never saved to disk (CD-CLM-07). Leash bindings live in the Cobblemon's `persistentData` (CD-LSH-07).
- One package (`pasture`) holds every read of Cobblemon pasture internals (ARCHITECTURE section 1).
- Engine work runs on the server thread only.
- Telekinesis, the Magnet, the Fan Catalyst and Tailwind are leash only: each role file has `"auto_assign": false`
  (CD-TLK-02, CD-MAG-02, CD-FAN-02, CD-TLW-02, R29).
- Telekinesis and the Magnet move at most ceil(64 × L ÷ 100) items in each 20-tick batch, so one worker moves at most 64
  items per second (CD-TLK-03, CD-MAG-03, CD-BAL-05, R27, R31, R52).
- Telekinesis and the Magnet never lose or duplicate an item, and they insert a copy of each stack (CD-TLK-07, CD-MAG-06).
- Telekinesis claims only its source. Only the source sits inside the work area. The destination sits within 32 blocks of
  the pasture block on each axis and is never claimed (CD-TLK-05, CD-TLK-09, CD-TLK-12, R54).
- Tailwind adds floor(S × L ÷ 100) virtual sails to a windmill with S real sails, and real plus virtual sails stay within
  128 (CD-TLW-03, CD-TLW-04, R30).
- Dynamics registers its fan processing types with a priority above 400 (CD-FAN-13).
- If a fan or windmill mixin fails to apply, its role turns off with one warning and the game does not crash (CD-FAN-17,
  CD-TLW-10).
- The action-bar texts are `"Select a destination for {Pokémon}"`, `"Destination must differ from the source"`,
  `"No room in front of the fan"`, `"{Pokémon} cannot reach {target}"`, `"Fan mode: Blasting"` and `"Fan mode: Smoking"`
  (R57). The refusals of CD-TLK-09 and CD-TLK-12 read `"Outside its pasture's work area"` and `"Too far from its pasture"`.
- No pixel comes from Mojang, Cobblemon, Create or AE2 (CD-ART-09). Every block and item texture is 16 × 16 (CD-ART-06).
  The source of every asset lives under `art/` (CD-ART-08). Phase 2 builds MAY ship placeholder art (CD-ART-11). The public
  release MUST NOT (CD-ART-12).
- Phase 2 adds no static mutable state. A task keeps new state in the engine, a claim memo, a Create block entity
  behaviour or an attachment.
- Quick Work takes only roles whose auto-assign flag is true, whose handler a pasture scan visits and that name one
  target, and it gives a Fairy-type no order. An order ends for good, and after its end no Quick Work code runs for its
  Cobblemon (CD-QWK-03, CD-QWK-05, CD-QWK-14, CD-QWK-24, R63).
- The Quick Work action-bar texts are those of CD-QWK-04, CD-QWK-06 to CD-QWK-11 and CD-QWK-13 to CD-QWK-22. Each of
  their lang keys takes the Cobblemon's name and then the target's name.
- Quick Work asks each loaded claim mod before an order starts and on every 20th tick of the order, and a check that
  throws refuses. Only `compat/ftbchunks/` and `compat/opac/` name a class of a claim mod, behind `ModList.isLoaded`
  (CD-QWK-26, CD-QWK-29, CD-QWK-30, CD-QWK-33, R64). CI does not run the two claim runs, so a pull request that touches
  the claims code runs `runGameTestServerFtbChunks` and `runGameTestServerOpac` and records both results in its body.

**Multiplayer.** Approver, 2026-11-10: "this MUST work in multiplayer. I don't see any issues for it and I do not want to
test that specific functionality, but we should make sure the code is made in-mind for multiplayer." Approver, 2026-11-10,
on testing: "no multiplayer game tests, we don't have that capacity. just make sure you're confident in the code." Every
feature works on a dedicated server with many players, and in singleplayer through the integrated server. Every task
follows these rules:

- The server owns all game state, and the client only displays it. No client code decides a bind, a claim, a mode, a
  bonus or an amount. Clients get state through synced attachments, Create block entity packets, item data components and
  the mod's payloads.
- Per-player state is keyed by player UUID, or it lives on that player's own item stack. No code holds a single "current
  player".
- The server validates every payload from its own state: the sender's permission, distance, dimension and ownership
  (CD-SEC-01 to CD-SEC-08).
- Payload handlers run their game logic on the server thread. A handler registers with `PayloadRegistrar`'s default
  thread, `HandlerThread.MAIN` (the registrar's constructor sets it, checked with `javap`), and never with
  `executesOn(HandlerThread.NETWORK)`. Code on the network thread hands its work to `IPayloadContext.enqueueWork`.
- Client-only classes never load on a dedicated server. They live in `client/` and `mixin/cobblemon/client/`, and only
  code behind `FMLEnvironment.dist.isClient` names them. Code that runs on both sides, such as the fan processing types
  and the Create mixins, names no client class.
- Static mutable state is cleared on `ServerStoppedEvent`, because the integrated server stops and starts again in the
  same JVM.
- Effects and UI updates reach every player who should see them: effect packets go to every player within
  `effectBroadcastRadius` (CD-FX-08), Create state goes out through `sendData()` to every tracking client, and panel
  states go to every viewer of the panel.
- Owner and binder checks hold when two players share a pasture or a target. A check compares the acting player's UUID
  with the Cobblemon's owner, the binding's binder or the pasture's placer, or reads operator permission.

Each task checks its code against these rules by reading it, in its "Multiplayer check" step. Unit tests cover the pure
logic that a rule depends on. No task writes a GameTest with two players. M8 Task 6 audits the whole mod against the
rules, Quick Work included: its orders and aims, which the work engine keys by the Cobblemon's UUID with the owner's UUID,
are among the first points that the audit reads.

## How to execute this plan

1. Work milestone by milestone, in order: M6, M7, M8. Each milestone is one branch and one pull request into `main`:
   `m6-telekinesis-magnet`, `m7-fan-tailwind`, `m8-art-gate`. Quick Work is its own branch, `quick-work`, and its own pull
   request. It may run beside M8 Tasks 1 to 5, and it merges before M8 Task 6 starts. The M8 branch then takes `main`, so
   the multiplayer audit (Task 6), the end-of-phase pass (Task 7) and the Phase 2 gate (Task 8) cover Quick Work. The land
   claim checks and the load lines (R64, R65) come after M8 Task 8, on the branch `quick-work-claims`, in one pull request
   whose last task runs the Phase 2 gate report again.
2. Inside a milestone, execute the tasks in their numbered order. Each task is test-first: write the failing test, run it
   and see it fail for the expected reason, write the code, run it and see it pass, then commit.
3. At the start of each milestone, check every API reference that its tasks use against the jars that Gradle downloaded
   (the Gradle cache, `C:\Users\admin\.gradle\caches`). Each milestone file lists the references that this plan checked
   with `javap` on 2026-11-10 (the Quick Work file on 2026-11-11), and marks the others "(inferred)". Treat an inferred fact
   as unverified. Where the code differs from the plan, fix the plan text in the same commit as the code.
4. A task is done when its tests pass, `./gradlew build` passes, and the GameTests that it adds pass in
   `./gradlew runGameTestServer`. A milestone is done when its pull request is green in CI, every review thread is
   resolved, and it is merged.
5. Cite the spec rows in code only where a comment states a non-obvious invariant. Rows are cited in test names
   (`CD-TLK-03 a batch moves at most the rate`) and in commit messages.
6. Test scope. Approver ruling, 2026-11-09: "avoid game tests for high-confidence code. I'd rather test at the end and
   fix." Unit tests stay test-first. Write a GameTest only where the behavior against real Cobblemon, NeoForge,
   Minecraft, Create or AE2 is uncertain: the Brain and AI, navigation, Create kinetics, Create fans and contraptions,
   mixins, other mods' item handlers and undocumented platform behavior. For other code, such as registrations, data
   files, bind rules, commands and simple block entity reads and writes, defer the planned GameTest:
   - Mark the row in the task text: "GameTest deferred (high confidence): verified in the end-of-phase pass".
   - Add the row to the deferred list in M8 Task 7.

   No GameTest has two players (the approver's multiplayer ruling above). Run the full GameTest suite once at the end of
   each part of a milestone, not after every task.
7. Before M6 starts, `main` holds: the approver's play-test note for CD-REL-13 in `docs/testing/phase-1-gate.md`, the
   pull request of the approver's 2026-11-10 changes (no Burner Keeper, the Charge Cell, the creative tab), and the fixes
   of the separate multiplayer review of the Phase 1 code. The first commit of M6 adds any spec amendment of this index
   that `main` still lacks.
8. Follow the development notes for the machine: JDK 21 through `JAVA_HOME`, one JVM at a time on the shared machine, and
   the manual pull request steps of HAR-809.

## Test architecture

The [Phase 1 test architecture](2026-11-09-phase-1-plan.md#test-architecture) holds: unit tests with no game bootstrap,
the GameTest mod `cobblemon_dynamics_test`, the five floor templates, `TestKit`, the simulated restart and chunk unload,
and the three GameTest runs. Phase 2 adds these parts.

**Unit tests.** Each rule that a row states as a number lives in a pure class:

- the batch rate and the destination reach (`TransferParams`)
- the batch planner (`ItemBatch`), over fake containers whose items are strings, because an `ItemStack` needs the game's
  registries
- the canonical position of an inventory of several blocks (`InventoryBlocks`, ruling 5), over sets of positions
- the Magnet's query clock (`QueryClock`)
- the virtual sail formula and the sail-sweep spot rule (`TailwindMath`)
- the fan and windmill NBT rules (`FanNbt`, `TailwindNbt`)
- the flip permission (`FlipRules`) and the Work Mode button sprites (`WorkModeSprites`).

The mixin gates (CD-FAN-17, CD-TLW-10) extend `MixinGateTest`.

**Item GameTests** (`TelekinesisTests`, `MagnetTests`). A pastured Alakazam or Klink works real containers: a vanilla
chest, barrel and furnace, Create's chute, depot and item vault, and AE2's ME Interface block and cable part. The AE2 scene
places a creative energy cell, an ME chest with a 1k item cell and the interface, all touching, so they form one network
with no controller. The test reads the cell through AE2's API, which the full test mod has as `gametestCompileOnly`. Dropped
items are `ItemEntity` objects that the test spawns, with the pickup delay that the row names.

**How the Fan Catalyst rows are tested.** `CreateKit.fan` places an encased fan with a Create creative motor behind it,
at the RPM that the row names, so the fan blows out of its face. Items sit on a Create depot (`DepotBlockEntity.setHeldItem`)
or a belt (`BeltConnectorItem.createBelts` and `BeltInventory.addItem`) one block below the air current, where Create
processes them, or they drop as item entities. Two kinds of test use these scenes:

- Handler GameTests (`FanTests`, M7 Task 2) hold the catalyst on the fan's `FanState` directly, with no Cobblemon, and check
  what Create does with it: blasting, smoking, washing and haunting, the priority over a water source, Create's processing
  time, and the exemption of an entity that carries the fan worker mark.
- Worker GameTests (`FanCatalystTests`, M7 Task 3) bind a pastured Charmander, Squirtle or Gastly with the Work Leash and
  check the work spot, the demand, the flip and the exemption at 256 RPM.

The client rebuilds the air current itself. No GameTest runs a client, so the automated part of CD-FAN-14 is a unit test
of what the fan's packet carries (`FanNbtTest`), and the manual checklist holds the Demo.

**How the Tailwind rows are tested.** `CreateKit.windmill` places a windmill bearing that faces up and a flat sheet of
Create sail blocks on its face, with a shaft below the bearing. A test assembles the windmill with
`MechanicalBearingBlockEntity.assemble()`, or through the owner's empty-hand click for CD-TLW-05. Speeds come from the
shaft's `getSpeed()`. A Pidgey stands beside the bearing, under the sails: its body is 0.7 blocks high, so the sail-sweep
rule allows the spot.

**Art checks.** `scripts/art.py check` reads the sources under `art/`, the shipped assets, the review record and, with
`--references`, the textures of Minecraft 1.21.1, Cobblemon 1.8.4, Create 6.0.10 and AE2 19.2.19 from their jars in the
Gradle cache. It prints one `CASE cd-art-NN: PASS` or `FAIL` line per row and decodes PNG files with the standard library.
A prototype of its decoder read all 12,088 reference PNGs in 38 s on the dev box. `ArtFilesTest` repeats the size, source
and license checks in `./gradlew build`, so CI catches them.

**How the Quick Work rows are tested.** `QuickWorkTests` (Quick Work Task 3) presses the R key through Cobblemon's own
server handler, `SendOutPokemonHandler.handle`, for a fake owner who looks at a furnace. `TestKit.listedOwner` puts the
fake player into the player list's UUID map, because Cobblemon finds a party Cobblemon's owner, and Quick Work finds the
owner of an order, through `PlayerList.getPlayer`. The tests run in their own batch, `quick_work`, and read the
action-bar messages from `Feedback.recorded`. The pure start and end rules are unit tests (`QuickWorkRulesTest`). The
GameTests of the refusals and of the other ends wait for the end-of-phase pass. The cost with no order is an Analysis
over the reference world of CD-PERF-01.

**Multiplayer.** No GameTest has two players. Each task's "Multiplayer check" step reads the code against the Global
Constraint rules. M8 Task 6 audits the whole mod and fixes what it finds, with unit tests for the pure logic that a fix
changes. The isolated test pack's `smoke` command starts a dedicated server with the mod, which shows that no client class
loads on a server.

**How the land claim rows are tested.** A test claim provider of the full test mod, `TestLandClaims`, tests the engine
path with no claim mod: the refusal at the start, the end within 20 ticks and a check that throws. Two runs test the real
claim mods: `runGameTestServerFtbChunks` with FTB Chunks, FTB Teams, FTB Library and Architectury API, and
`runGameTestServerOpac` with Open Parties and Claims. Each loads the mod set of the core run and one claim mod. Their owners
are of the exact class `ServerPlayer` (`TestKit.plainOwner`), because Architectury counts every subclass as a fake player.
Each test has its own batch, because a land claim covers a whole chunk. The test pack starts a dedicated server with each
claim mod and checks, from the class load log, that the compat classes of the absent mod never load (CD-QWK-33). By the
coordinator's ruling of 2026-11-11, CI does not run the two claim runs. They run in the pull request of the claims file,
in each later pull request that touches the claims code, and at each phase gate, whose report lists them. CI runs the
test claim provider with the full run.

**Run matrix.** The three Phase 1 runs stay. In the core run (no Create, no AE2), the Telekinesis and Magnet roles are
active, and the Fan Catalyst and Tailwind roles are off (CD-CFG-10, CD-PLAT-05). The two claim runs come with the
[claims file](2026-11-11-phase-2-quick-work-claims.md). CI runs every GameTest run except the two claim runs.

## Design decisions for the approver

The plan makes these calls. Each milestone file gives the detail.

1. **Three Fan Catalyst role files.** The Role table gives the Fan Catalyst one effect per type, and a role file holds one
   effect. So `fan_catalyst_fire.json`, `fan_catalyst_water.json` and `fan_catalyst_ghost.json` share one handler, and each
   names its catalyst in `params`. A Cobblemon with two of the types gets the role of its primary type, then of its secondary
   type (ruling 1 below, which replaced the id order of CD-LSH-16 here). A data pack changes that order with `priority`.
2. **The fan worker mark lasts for the whole work claim.** A spinning fan pushes a worker that walks to the block in front
   of it, so the mark holds from the claim (Traveling, Standby and Working), not only while the worker Works. The marked
   worker is exempt from every encased fan's air current.
3. **The air current mixin targets `AirCurrent`.** `javap` shows that `findEntities` and `caughtEntities` live in
   `AirCurrent`, not in `EncasedFanBlockEntity` as ARCHITECTURE section 8 says. The mixin injects at the head of
   `tickAffectedEntities`, so a new mark takes effect on the next tick. Phase 2 adds no nozzle mixin. A nozzle fills the
   block in front of its own fan, so a fan with a nozzle has no catalyst worker. M7 corrects ARCHITECTURE and ADR-0011.
4. **Only a fan that faces sideways takes a worker.** The block in front of a fan that faces up is on top of the fan, and a
   spot never stands on its target (CD-ASG-09). A fan that faces down leaves no room for the worker's head. Both get
   "No room in front of the fan".
5. **Tailwind spots stay out of the sails.** A Tailwind worker stands beside or behind the bearing's face. Under a
   windmill that faces up, a spot needs room below the sails for the worker's body. Assemble the windmill before you bind,
   because sail blocks fill the cells around the bearing until then.
6. **The fan catalyst and the Tailwind bonus lapse on their own.** As with the Blaze Burner heat, the handler renews each
   one on every Working tick, and the block entity behaviour clears a value that was not renewed. A release that never
   came therefore leaves no catalyst or bonus after 2 ticks.
7. **Reachable work spots.** A claim checks a path to at most 3 spots, best first. A target whose 3 best spots have no
   path is skipped for `retryWaitTicks`, as after a travel timeout. A spot beyond the worker's follow range counts as
   reachable, because the pathfinder does not plan that far.
8. **Silent Phase 2 effects.** Telekinesis sends only `cobblemon:kinesis_actorspiral`, because the file of
   `cobblemon:kinesis_actor` plays a sound (CD-FX-09). The Water Fan Catalyst sends no target particle, because Bubble's
   target particle `cobblemon:bubble_target` has no particle file in Cobblemon 1.8.4. The Magnet plays `special` with
   `cobblemon:metal_sparks` at its container.
9. **Levels above 100.** Telekinesis, the Magnet and Tailwind clamp a level to 1 to 100, so a raised level cap never breaks
   CD-BAL-05 or the 128-sail cap.
10. **A rendered review spritesheet.** `py scripts/art.py review` renders the Work Leash, the creative tab's icon, the
    leash candidates and every UI sprite from their sources, at 8x and 1x on a light and a dark inventory slot, each with a
    label, and shows each block item from above for reference. It needs no game client, which the shared machine has
    little memory for. The approver sees the assets in the game during the Phase 2 play-test.
11. **Quick Work.** The [Quick Work file](2026-11-11-phase-2-quick-work.md#design-decisions-for-the-approver) lists the
    calls that it makes beyond the rulings of R63: the aim at the key press, a server switch, the leash measure, the
    ranges, no Quick Work for Fairy-types, a quiet send-out, the extra ends, no flip and no made-up click. The coordinator
    kept all nine calls on 2026-11-11, under the approver's delegation.
12. **Land claims.** The [claims file](2026-11-11-phase-2-quick-work-claims.md#design-decisions-for-the-approver) lists
    the calls that it makes beyond the rulings of R64 and R65: an empty main hand, the whole permission every 20 ticks, the
    message of FTB Chunks, optional entries with any version in `neoforge.mods.toml`, the canonical block, test owners of
    the exact class `ServerPlayer`, two GameTest runs outside CI, a test claim provider and the times of the load lines.
    The claims file records the coordinator's rulings of 2026-11-11, which changed two calls: the entries in
    `neoforge.mods.toml`, and the claim runs outside CI.

## Rulings on the plan's open questions (2026-11-10)

   the id order of the role files. A Fire and Ghost type gives fire, and a Ghost and Fire type gives ghost.
2. **Fan direction.** Only fans that face sideways can take a worker. A worker standing in an up or down air current would

## Logistics roles share their containers (R66, 2026-11-11)

Input R66 of the spec sheet holds the approver's ruling of 2026-11-11 and the coordinator's rulings on it, under the
approver's delegation. The Magnet and Telekinesis share their containers. Up to `logistics.maxWorkersPerContainer`
workers (default 5) work one container at once, counted across both roles at its canonical position. The work is the
branch `logistics-shared-targets`, from the land claims branch (PR #30), and it builds `1.0.0-beta.3`.

- **The handler marks the sharing.** `TargetHandler.sharesTargets` is true for the Magnet and Telekinesis handlers. A
  role file that names either handler is a logistics role, and a new handler opts in the same way. The engine names no
  role id.
- **Claims.** The claim registry keeps shared claims apart from exclusive claims, and it refuses a shared claim only at
  the cap. Exclusive claims, and the reservations of exclusive bindings, never meet shared claims (CD-CLM-11). Before
  this change, one claim and one binding of any role held a canonical block, so a Pump and a Telekinesis worker refused
  each other on a Create basin.
- **Bindings.** The leash index holds several entries on one target, and the destination of each Telekinesis entry. A
  bind of a logistics role counts the places that the other bindings take at each container that it names, and it
  refuses at the cap (CD-LSH-29). A bind of an exclusive role meets only exclusive bindings.
- **No change** to work spots, the item batch or Quick Work. Each worker needs its own free spot, every move runs on the
  server thread through one batch, and Quick Work never starts a logistics role.
